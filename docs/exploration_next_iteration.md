# Explore 下一轮优化清单

本文件保留实施前规划及阶段性记录。当前二阶段见 exploration_workflow_current.md；第三阶段按 script_generation_current.md 实施，不再沿用下文旧 review 流程。

依据：首轮重构后围绕工具选择、上下文、轨迹、验证位置与 Observe 的讨论。

本文件整理下一批设计与实施任务，尚未实施。它补充已有设计，最新用户确认优先；不能把讨论中的建议视为已经验证的能力。

## 1. 保持不变的约束

- 服务只整理、探索、生成一个用例；每个 step 只探索一遍。
- repeat 只作用于代码生成；轮内明确的手势次数与时长需要完整执行。
- 第二阶段不执行业务断言、不改写用户预期；保存第三阶段需要的事实与定位上下文。
- 原始轨迹完整保留，最终脚本的路径筛选在第三阶段进行。
- 插件继续看到详细决策简述、执行结果、截图、进度、恢复和阻塞事件。
- 整理入口与执行前解析共用 CaseParser；第一阶段只补充本轮真正需要的语义，不恢复批量接口。

## 2. 讨论已明确的方向

1. 工具实现规则必须保留。例如“启动应用”应调用 StartApp，不由模型随意选择桌面点击替代。精简 prompt 不能删掉脚本稳定性要求。
2. 每次模型请求可以使用清楚的当前任务状态；不必同时维护动作摘要、完整工具对话和另一套可修改的进度记录。
3. observations 与 operations 通过 ID 关联，不依赖数组位置或长度不变量。
4. 每个手机动作后系统自动取得新观察；模型只在需要时请求额外观察。
5. 模型要请求额外观察，需要显式工具或决策接口；继续 tool calling 时应增加 Observe。
6. Observe 是采集控制，不应伪装成手机操作，更不能直接生成脚本动作。
7. 第二阶段的数据契约需由第三阶段的真实需求反推；原始意图、执行事实、审查结论分别记录。

尚需定稿的选择：普通指令是否仍要求单独 CompleteInstruction；动作决策如何携带进度更新；全局背景的最小字段；少数特例的工具策略。下面给出建议基线，实装前先固定它们，避免边写边改接口。

## 3. P0：先收紧探索交付契约

目标：第三阶段能理解操作依据、有效路径、验证位置和缺失证据，同时 state 不重复维护同一事实。

- [ ] 定义 OperationRecord 与 ExecutionResult，替换裸 dict 列表的关键部分。
- [ ] 规范执行结果状态：pending/succeeded/failed/unknown；必要的 success 兼容值在边界派生，不独立维护。
- [ ] OperationRecord 保留 step_id/instruction_id、前后 observation ID、规范动作、执行结果与时间、命令引用、简短决策说明。
- [ ] 真实下发参数与模型请求参数确有差异时分别记录；原始 tool payload 放可选 debug 引用，避免核心里复制三套同义参数。
- [ ] Observation 定义采集时间、采集原因、截图/UI 资源、质量限制；它是一次采集，不是一个唯一页面。
- [ ] 运行状态增加 current_observation_id，不再在各处隐式用数组最后一个元素表达当前页面。
- [ ] StepResult 补指令完成情况和观察边界；不将“命令成功”或模型摘要等同于业务目标成立。
- [ ] 检查点统一保存于 exploration_result.verification_checkpoints；通过 verification_id 引用 CaseSpec，不复制预期文本。
- [ ] 检查点记录 observation_id 与可用的 after_operation_id，允许初始边界没有前置动作。
- [ ] 无图、无树、采集失败、结果未知、未完成内容使用明确限制说明，不通过空数组掩盖。

建议交付骨架：

```text
ExplorationBundle
  schema_version
  case_spec
  exploration_result
    status
    trajectory
      observations
      operations
    step_results
    verification_checkpoints
    limitations
```

原始 CaseSpec、轨迹、生成后的 IR 含义不同，不因为字段相似而合并。上下文摘要、查询索引和展示 payload 可以派生；不把这些视图当第二份可独立编辑的事实。

清理项：completed_steps 从 step_results 派生；operation.step_goal/matched 退出；intent.tool_args 与 raw_tool_call 的重复内容归 debug；移除投影里的 source_path/repeat_context，统一 step_id 名称；Run 返回值的 trajectory 与 explorationResult.trajectory 只保留一个正式来源。后者涉及插件消费，需配套更新或明确的边界兼容。

## 4. P0：明确工具策略与单轮决策协议

- [ ] 列出已有工具规则，分别标为“强制方法”“选择偏好”“条件例外”，保留用户原来的有效经验。
- [ ] 第一阶段识别必要的语义类别，如启动应用；第二阶段把类别映射到执行工具，不让第一阶段依赖插件方法名。
- [ ] 能确定方法与参数的操作可由程序构造；需要页面判断的操作交给模型。
- [ ] 强制策略在执行前检查，不能只在 prompt 提醒；规则作用于当前语义操作，不能限制整个 step 后续正常动作。
- [ ] 明确桌面图标交互本身是测试对象等场景的边界，不把不同用户意图强行改写为启动 API。
- [ ] 保留 instruction 的有序要求与追溯信息，重新决定进度报告方式。

建议：普通指令完成信息随下一次动作决策报告；有验证检查点时明确交接，先绑定观察再离开。不要机械地为每条指令增加一次控制调用，最后再追加一次等价结束调用。但在进度协议定稿之前，不直接删掉现有 CompleteInstruction，避免丢失边界。

## 5. P0：把上下文改为状态式输入

建议每次发送 system + 一份多模态 user 状态，继续使用 tool calling 输出动作，不再默认回灌完整 assistant/tool 历史。

```text
固定规则：操作职责、强制方法、结果与页面的使用原则

当前状态：
  必要全局背景：应用、跨步骤对象/参数与前序实际出口
  当前 step：单轮目标、有序要求与原值参数
  进度：已完成、进行中、待完成、明确计数
  最近结果：实际动作结果，以及有效的失败/恢复记录
  当前 observation：ID、截图、必要页面元数据
```

- [ ] 上下文由轨迹与权威进度构建；模型摘要可辅助理解，不能取代实际执行结果。
- [ ] 区分“动作已下发”“命令成功”“操作目标已完成”，不在摘要中混为一谈。
- [ ] 保留累计次数和关键失败策略，不因最近动作裁剪而遗忘；插件未确认的次数不得记成已完成。
- [ ] 移除最近六动作摘要与最近八工具回合的重复；不要简单删历史却不补持久进度。
- [ ] 不向操作模型发送 repeat、验证预期、框架 API、IR、插件展示协议或产物路径。
- [ ] 用当前完整请求检验清晰度，包括工具 schema，不只优化 system 文本长度。
- [ ] 允许特定难例定向补充证据，不预设所有场景都必须携带同一种历史形式。

## 6. P0：动作后自动观察，按需额外 Observe

- [ ] 将 execute → 等待/采集 → 返回执行结果与主观察，封装为一致的系统路径。
- [ ] 增加 Observe 工具，参数为 reason 和可选的短等待；利用现有插件截图/UI 能力即可，不要求插件新增同名工具。
- [ ] Observe 新增 observation 并更新当前引用，不进入 operations；详细事件仍向插件展示。
- [ ] 用户明确等待与探索刷新等待分开；前者进入脚本语义，后者不直接成为固定 sleep。
- [ ] 工具说明明确：手机动作后已经自动观察，无需例行再调用 Observe。
- [ ] 连续观察次数、总等待时间有预算，避免观察空转。
- [ ] before_observation_id 表示动作依据，after_observation_id 表示动作后选定的主观察；额外帧可保留，不强制一动作一帧。
- [ ] 重复观察、动作后采集失败都合法，通过引用和时间校验，不再要求 len(observations)=len(operations)+1。

现有明确问题：模型返回后无条件以 30 秒判过期，会让持续推理超过 30 秒的模型反复重拍且无法执行。需调整为合理的时效/变化判断与有界重决策；不能让刷新流程无限拒绝动作。

页面稳定判断也不能只靠固定 sleep 或像素完全一致。先建立可操作页面的有界等待机制，保留瞬时提示需要的早期观察；组合采集与更精确时序属于插件能力增强。

## 7. P1：生成前路径与验证边界审查

- [ ] 审查输入保留失败/未知动作上下文，不能在理解路径前一律过滤。
- [ ] 以完整错误/恢复片段判断是否删除，并检查保留路径能否衔接。
- [ ] 加入必要的前后页面证据，不只相信模型当时写的 reason。
- [ ] 正常业务确认、必要返回与环境处理分别判断，不按工具名或关键词全部删除。
- [ ] 筛选后检查指令覆盖和验证边界；引用已删除片段时需有依据地重关联或报告证据不足，不能静默移到末尾。
- [ ] 定位层区分指定对象、序号对象、动态标签；同页唯一不等于跨次稳定。
- [ ] 用户验证预期、参考定位与执行观察分别表达。没有匹配控件不意味着验证应删除或预期可以改写。

本轮第三阶段主要处理上述消费契约和必要校验，不全面重写框架 profile 与代码组织策略。审查结果引用原始 operation，不回写篡改轨迹。

## 8. P1：Prompt、事件和测试同步

- [ ] system 保留真正影响脚本稳定性的规则；工具局部约束放 schema，动态状态放 user 输入。
- [ ] 清除与实现不符的承诺，例如“自动等到页面稳定”“未知结果后可继续核对”却没有对应机制。
- [ ] reason 简短表达可见依据和动作目的，不承担次数账本、完整状态或断言描述。
- [ ] 节点、控制工具、Observe、执行结果和页面采集事件均向插件可见；不用模型上下文的精简替代插件过程展示。
- [ ] 测试覆盖启动方法强制、连续两次观察、无动作观察、慢模型、加载后观察、截图失败、指令计数、错误路径与验证边界、单轮探索和循环生成。
- [ ] 先用假模型/假设备检查协议，再基于固定截图和真实流程比较效果；不把测试通过视为真实生成效果已经证明。

## 9. 推荐实施顺序

1. 固定本轮交付契约、工具策略与进度协议。
2. 同步修改状态构建、Observe 和块内循环；验证第三阶段仍能消费结果。
3. 配套修改第一阶段必要语义与全部相关 prompt/schema。
4. 增强路径审查、定位与检查点连续性验证。
5. 清理重复字段、过渡兼容和文档，再做少量真实联调。

暂不扩展：批量用例、循环探索策略、自动执行业务断言、完整测试执行框架。草稿免二次解析、插件原子组合采集和命令结果查询另列后续能力，不阻塞本轮基本流程。

## 本轮实施状态

已接入：独立方法策略、Observe 及预算、状态式上下文、前置过期刷新、随工具报告指令完成、进度与检查点独立模块、OperationRecord 和引用校验、审查执行结果及页面标签、保守 UI 路径/覆盖/检查点校验。

并非所有增强项均完成：精细参数与次数账本、自适应稳定等待、跨步骤对象记忆、统一状态枚举与剩余冗余返回、动态定位评估仍需继续完善。路径检查只使用 UI 证据，不证明业务状态等价；目前采用显式拒绝无法确认的删减，未引入自动修复。
