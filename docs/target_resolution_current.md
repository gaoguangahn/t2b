# 第三阶段目标解析与验证

更新：2026-11-13。

## 控件数据入口

`ui/elements.py` 负责统一插件字段、布尔值、节点层级，以及将插件的设备像素 bounds 转成 0～1000 浮点坐标。`ObservationStore.observe()` 在采集入口调用一次，随后将标准列表保存到 `DeviceObservation.elements`。各阶段和轨迹读取直接使用保存的数据，不重复标准化，不猜测坐标单位，也不同时保存一份像素 bounds。

`node_path` 保留插件过滤前的原树路径；`parent_id` 指向最近的已保留祖先，不要求直接父节点仍在列表中。没有路径时不使用旧的父 ID 字段，也不按矩形覆盖猜测层级。节点 ID 只在所属 observation 内有效，路径不用于脚本定位。无效 bounds 标记为 null，不删除同一节点上仍可用的文字或状态证据。

完整列表用于保留现场。探索上下文可以按状态意义排序、裁剪输入，但不改写快照；`checkable=true` 的控件优先，普通节点的 `checked=false` 不能代表开关关闭。需要像素时使用 `ui/coordinate.py` 的 `to_pixel_bounds(bounds, screen_size)`，返回新列表，不修改快照。双向转换保留小数；没有有效屏幕尺寸时明确报错，不悄悄返回另一种单位。目标筛选调用位置及模型调用次数保持原状。

## 目标与调用

动作计划完成后，每个点击、双击、长按、执行条件或用户验证各调用一次目标解析模型。定位和验证策略在同一份 TargetResponse 返回，不额外增加复核模型。滑动、输入等动作不查点击控件。

动作固定使用操作前帧；条件固定使用组内第一个动作前帧；验证固定使用对应 checkpoint。锚点丢失时返回 unresolved，不借用最终页面。

context.py 根据原始证据临时构造输入，不写回探索轨迹或全局 state：

- 用户目标、整理描述、固定 observation_id、屏幕像素尺寸、原操作的 0～1000 区域。
- 锚点已保存的全部标准控件，包含状态属性、可用 parent_id、单属性匹配数，以及点击目标的空间关系和排序参考。
- 当前操作，或验证锚点之前同指令/目标块内最近两个相关操作的实际参数、reason、执行状态、前后观察引用。
- 同一稳定属性在前后帧各唯一时形成控件对应；保留 checked/selected/enabled/文本等实际变化。缺失属性为 null，不能默认 false；对应或变化本身不证明操作成功。
- 最多五帧 UI（锚点加两个操作的前后帧）；视觉模型最多附三张带观察 ID 的图片。验证不带锚点之后的帧。相关且已被动作计划保留的操作 ID 单独列为允许的运行时基准。

这会增加单次调用的证据量，调用次数不增加。相关动作范围有意受限；跨步骤基准或未提供的对象不能猜测补齐。

## 点击区域与稳定定位

ui/spatial.py 的输入和目标上下文统一使用 0～1000；模块内部按屏幕尺寸计算像素距离，避免宽高比例导致距离失真，模型不需要重复转换坐标。候选包括覆盖原框中心、交叠面积至少达到较小矩形面积的 20%，或未相交但距离不超过屏幕短边 1.5%（最低 4px）的控件。仅少量擦边交叠不算充分依据；候选占全屏超过 70% 且原框不到其面积 10% 时视为过大容器。

这些阈值提供空间线索，不证明语义正确。模型仍需判断交互对象：同行标签、开关本体、装饰文字可能位置接近却功能不同。排序不是允许名单，也不会让程序自动选择最近的节点。来源 UI 的 bounds 不可用时不能用空间推测补证据。

模型先选候选 ID 和属性名，locators.py 从现场复制值。重复时尝试为同一节点补充最小稳定属性组合；有明确父节点关系时尝试稳定所属区域。不切换成另一个节点，不固定全局第一个匹配。

attributes/scope_attributes应选择对应节点有非空现场值的属性，不要求四种属性全选，一个属性满足语义、稳定性与唯一性即可。程序先过滤所选属性中的null、空字符串与未提供字段并去重，再继续原有稳定性、唯一性、区域和用户位置要求检查。空值或重复项不再使整个组合直接失败；不会换候选、删除有值的定位限制，或丢掉整个所属区域来绕过校验。未选属性或所选属性全无现场值时仍报告来源观察、候选ID、所选属性和可用属性名；仅本帧唯一的动态内容仍会被拒绝。

点赞数量、价格、时间、输入推荐词、列表随机标题等保护仍保留。自动补充文本/描述限于用户明确提及的原文，其余需模型明确选择并经过稳定性检查，避免程序为了本帧唯一而擅自绑定昵称、标题或状态文案；明显动态 ID 也不自动补充。用户明确指定原文和序号的语义继续保留；scope_index 与目标 index 不混淆。完全相同且无法稳定消歧时保留坐标与限制，由生成结果标记草稿。

## 验证策略

正式契约在 contracts/script.py 的 VerificationPlan；只存一次，位置为 VerifyNode.target.verification。VerifyNode.expectation 保留用户完整原预期，TargetResolution.observation_id 仍是原锚点。模型协议私有字段 candidate_observation_id 只用于选择来源控件，不再复制为一份全局状态。

| method | 含义 | 关键约束 |
| --- | --- | --- |
| attribute | checked/selected/enabled 状态比较 | 源控件确实提供布尔属性，预期来自用户 |
| ui_feature | 明确等价状态文案/描述存在或不存在 | 定位含真实状态文案/描述，不能只检查开关 ID 存在 |
| text | 文本比较 | equals/not_equals/contains，预期字符串 |
| number | 有明确格式与单位的数值比较 | 不能固定探索快照值或猜测数值单位 |
| count | 匹配集合数量比较 | 保留完整集合，允许多个匹配，不加索引或自动缩成一项 |
| unresolved | 无可靠证据或实现方式 | 记录缺口与 notes，保留用户要求 |

number/count 的 delta 必须引用允许的 baseline_operation_id，脚本在该动作前读取实时基准，再于原验证锚点比较。其他方式不携带基准 ID。

如果当前缺少预期特征，但已提供的历史帧记录了它的真实属性，可以引用历史候选作为定位依据，脚本仍在原锚点检查实时状态。历史定位在锚点引入多个不可区分的匹配时拒绝。历史特征存在不代表当前断言通过，当前未出现也不能改写预期。

例如 Wi-Fi 验证可读取开关 checked，或使用有依据的“WLAN已关闭”状态提示；“未连接网络”并不能证明开关关闭。没有 checked 不等于框架不能验证，只有颜色差异且无可读取状态/明确文案/已有图像资源时也不能编造能力。

verification.py 只检查策略组合、实际属性和引用来源，不比较现场值与预期。编码阶段按 profile 选择 obj.info、get_text、count、exists 或 wait_ui；等待器不支持的限定或状态属性不强塞参数。框架确实缺少能力时保留 TODO 和 notes，不删除验证或降低标准。

## 边界

长期稳定性与等价 UI 特征的业务含义仍需要模型判断；单次 UI 证据和本地检查不能证明全部运行环境下可靠。空间容差也不保证可以替换所有错误框选。没有增加自动补探索、业务断言执行或自动修正用户预期。

旧数据可不带 target.verification，继续按原预期编码；新字段是兼容性增加。插件仅显示脚本与状态时无需改接口；若解析 IR，应允许这个新增字段。
