# 前两阶段的提示词与上下文设计

历史设计稿。当前提示词已实施；实际职责、消息和限制见 exploration_workflow_current.md、script_generation_current.md。

日期：2026-11-11。设计稿，未替换当前生产提示词，也未验证真实模型效果。需与契约、工具 schema 和上下文构造同步实施。

## 1. 实施范围

第一批重构以第一、二阶段为主体，同时完成第三阶段对新 CaseSpec/ExplorationResult 的必要适配，不能让新数据继续进入旧字段读取逻辑。

第三阶段同步调整的范围：步骤关联、整块 repeat、验证 anchor/scope、检查点和定位证据读取，以及引用这些字段的 prompt。其独立的审查策略、定位策略和代码生成效果优化另开一批，不在前两阶段重构中全面重做。

提示词属于阶段实现的一部分，与数据结构、工具描述、动态上下文一起设计，不留到重构完成后才改文字。当前新增设计文档不代表已经开始代码重构。

## 2. 先明确每次模型调用的问题

| 调用 | 模型需要回答的问题 | 应看见的信息 | 不需要看见的信息 |
| --- | --- | --- | --- |
| 用例解析 | 这段描述包含哪些有序目标、原值参数、重复范围和验证位置？ | 本次输入全文、来源片段、语义整理规则、输出 schema | 手机工具清单、页面截图、插件协议、轨迹结构、框架编码规则 |
| 定向解析修复 | 输出中哪些结构错误需要修正？ | 原输入、上次语义结果、具体校验错误 | 每次完整追加所有历史报错或重新讲系统架构 |
| 块内操作 | 根据当前页面，为完成当前操作块下一步应该调用什么工具？ | 单轮目标、有序指令、明确参数、已完成事实、最新页面、必要近期历史、可用工具 | repeat 元数据、业务验证预期、代码框架、未来所有目标、产物存储路径、事件推送机制 |
| 无进展恢复 | 当前卡在哪里，有哪些尚未尝试的合理路径？ | 当前目标和页面、准确的失败/未知结果、已尝试策略和剩余预算 | 全用例重跑要求、与当前问题无关的历史事故规则 |

检查点的预期文本不传给操作模型；只传“完成 ins_002 后报告进度”这类必要的控制边界。模型无需知道报告进度是为了断言、截图还是其他后处理。

## 3. 当前提示词需要修正的内容

以下是静态审查发现的问题，不是对真实模型效果的实验结论：

- `prepare_cases.md` 将操作与验证拆成两个字符串数组，容易丢失中间验证位置；新输出要与统一 CaseSpec 对齐。
- `structure_cases.md` 仍称采样，并让参数全部写进 goal；这与独立 repeat、原值参数、块内指令和锚点设计不一致。
- 当前结构化提示词允许验证只归属某块，具体位置交给生成阶段猜；新设计必须在第一阶段表达位置。
- system prompt 与 `step_context.py` 重复讲“只做当前块、不要执行后续、动作后自动观察、完成后结束”等规则。
- “系统会自动等待页面稳定”超出了当前固定睡眠实际能保证的能力。提示词应准确描述观察机制，不把假设写成事实。
- 固定要求返回时优先点页面按钮、黑屏时先 Back，以及把各种权限/登录页面都当干扰，容易把特定案例的处置经验变成所有任务的默认动作。
- reason 同时被要求描述完整语义、避免剩余次数，又承担审查线索。应让结构化参数和进度账本负责次数，reason 简述当前证据与动作目的。
- 输出 schema、字段名、合法 JSON 等格式要求多处重复。字段形状主要交给工具/结构化输出 schema，正文着重表达语义边界。
- 当前上下文类的注释描述“固定任务单独一条消息”，实际实现却把任务与当前截图放到同一条消息。重构时应让文档、构造器与实际请求一致。

## 4. 第一阶段：用例解析提示词草案

模型输入是一条用例的完整文本；若上游已拆分多条用例，程序逐条处理，不让模型再次决定跨用例拆分或合并。

建议 system 核心正文：

```text
将给定用例描述整理为有序的业务操作块和验证意图，按提供的 schema 返回。

保留原意：
- 不新增或删减业务操作、测试数据和验证预期。
- 输入文本、应用名、目标名称、次数、方向、时长和间隔保留原值。
- 信息缺失或范围不明确时记录具体 issue，不自行补值。

组织操作：
- 一个 step 表达一个业务目标或一轮完整流程；goal 描述这一轮内容。
- instructions 保留用户明确要求的内部顺序和参数，不预先猜测 UI 入口或坐标。
- 整组业务流程的重复次数写入 repeat，不展开多个 step，也不重复写进 goal。
- 连续滑动次数、等待时长等属于轮内参数，不能转成整个 step 的 repeat。

组织验证：
- 操作与验证按语义区分，不能只按“确认”“检查”等词分类。
- 验证保留用户预期，标明 before/after 锚点以及循环内外作用域。
- 块内验证关联具体 instruction；需要导航才能验证时，导航保留为操作。
- 不判断预期是否正确，不生成脚本，不选择手机工具。
```

字段解释放在 schema 的 description 中，例如 anchor 的合法指向和 scope 取值；不要在正文再复制整份 schema。精确输出约束由结构化输出机制执行，程序仍检查引用与业务规则。

user 内容只放：用例文本、必要的来源片段 ID，以及用户明确提供的上下文。版本号、运行 ID 和存储信息由程序管理。

需要示例时，只补充当前模型容易混淆的少数对照，例如“确认订单按钮属于操作”“循环内检查应锚定内部指令”“上滑 5 次不等于整个流程重复 5 次”。不要把大量具体应用导航案例塞进通用 prompt。

解析复核只针对忠实性：有没有漏掉操作、改写字面值、改变重复范围或移动验证。它不评判用户用例正确与否。

## 5. 第二阶段：块内操作提示词草案

### 5.1 固定 system

```text
根据当前手机页面完成给定操作块。每轮只调用一个可用工具。

- 按指令顺序推进，只执行当前块的一轮内容。
- 当前 observation 是页面事实；历史中的动作意图不代表动作已经达到目标。
- 使用指令中的原值参数，不改写输入，不替换目标对象或应用。
- 可以执行完成当前指令必需的聚焦、导航和恢复动作，不增加新的业务目标。
- 指定指令要求报告完成时，先调用进度工具，再继续后续指令。
- 全部指令完成后调用 CompleteStep，概述实际完成情况；当前状态已满足导航指令时可引用页面证据，无须重复操作。
- 失败或页面无进展时结合新观察调整策略；结果未知时先核对，不盲目重复提交。
- 无法继续时调用 ReportBlocker，说明实际缺口与已尝试的操作。
```

这是与目标工具接口配套的草案。CompleteStep/ReportBlocker 等名称必须与实际 schema 一致，不能先换 prompt、运行时仍只识别旧 FinishTask。

system 不讲脚本 IR、框架方法、repeat、数据库或事件发布。即使系统最终目的是生成脚本，当前模型也只需知道自己负责的操作任务。

### 5.2 当前任务消息

以下是渲染后的示例，不是新增一份用户可编辑的业务数据：

```text
当前操作块 step_002
目标：搜索手机后返回首页。

按顺序完成：
ins_002：搜索指定关键词。输入原文：手机。
ins_003：返回应用首页。

完成 ins_002 后先调用 CompleteInstruction 报告完成，再执行 ins_003。

当前进度：
ins_002：进行中，已聚焦搜索框，尚未输入和提交。
ins_003：未开始。
```

其中不出现“重复 5 次”“验证包含手机壳”“为了后面生成脚本”等内容。若采用参数引用工具，任务显示参数 ID 和原值，工具通过 ID 绑定，程序解析真实参数。

已完成块只提供与当前位置有关的简短实际结果。当前块的完整指令一直保留，详细原始动作不重复渲染成第二份长历史。

### 5.3 近期动作与当前观察

消息结构固定为：

```text
system：固定操作职责
user：当前任务、参数和权威进度
assistant/tool：最近若干个完整动作回合
user：最新 observation ID、截图、必要元数据
```

tool 结果只提供会影响下一次决策的信息：执行状态、实际结果消息、计数、必要错误。原始工具响应和完整 operation 进入轨迹与插件事件，不全量回灌模型。

最后一条消息明确哪张图是当前页面；补充历史图只用于具体恢复问题，并标明其历史身份。模型不需要了解图片文件路径或 base64 存储方式。

### 5.4 工具说明与输出责任

工具 schema 负责局部语义：Click 的 bounds 坐标空间、InputText 的引用/原文参数、Swipe 的方向次数间隔、进度工具的完成边界。通用 system 不再重讲每个工具的全部参数规则。

reason 用一句可供用户阅读的动作说明，例如“首页可见搜索入口，点击进入搜索页”。不要求模型输出长篇推理，也不强迫它为每次动作复述整个目标。实际参数、已执行数量和完成依据由对应结构保存。

CompleteStep 报告操作完成，不宣称业务成功。CompleteInstruction 只在需要中间交接时使用，不执行断言；程序绑定当前观察后返回可继续的信息。

工具 schema、prompt、决策解析和事件展示必须同步变更，不留下旧名称、新参数和旧解析器混用的过渡状态。

## 6. 程序与模型的职责划分

| 程序负责 | 模型负责 |
| --- | --- |
| step 顺序与每块一次 | 理解当前页面与当前目标的关系 |
| repeat 元数据留给生成 | 决定具体入口、点击位置和合理导航 |
| 引用合法性、字段类型、坐标范围 | 识别可见控件与操作上下文 |
| 原值参数解析、数量累计 | 解释当前动作如何推进用户指令 |
| 验证边界与证据绑定 | 在要求的边界报告指令完成 |
| 轮次/超时/恢复预算 | 识别阻塞并说明已尝试路径 |
| 事件推送、快照、产物路径 | 提供简短、基于观察的动作说明 |

不让 prompt 承担程序能够直接保证的硬约束。程序也不把“有一个成功点击”机械等同于语义目标完成；需要结合进度报告和页面证据。

## 7. 优化与验证方式

提示词按模型实际收到的完整请求检查，包括 system、task、工具描述、tool 结果、图片和历史；不能只审阅某个 md 文件。

第一批固定以下关键场景：

- 输入含引号、空格和特殊字符，参数从解析到工具调用保持一致。
- 业务 repeat 与滑动次数同时存在，探索只执行一轮，轮内次数完整。
- 循环内部验证不会使模型提前结束，也不会漏掉后续返回操作。
- 实际提示与预期不同，操作模型按实际页面推进，验证意图保持不变。
- “确认订单”不会因关键词被移成验证。
- 长块中早期动作退出历史窗口后，指令进度仍准确。
- 截图变化或命令结果未知时，不沿用旧页面假设重复操作。
- 模型返回的工具与完成状态能被实际解析器识别，插件看到对应的完整进度事件。

先用请求捕获与假设备验证上下文契约，再对固定输入/截图做小规模真实模型比较。记录语义保留、动作选择、漏步/重复、额外调用和耗时。降低 temperature 或缩短 prompt 都不自动等于效果提升，最终以固定样本与真实流程结果判断。

关键失败样本用于修正职责、数据或局部工具描述；只有确认属于可泛化的决策规则时才加入 system。避免每遇到一个问题就永久追加一条全局例外。

## 当前稳定路径目标下的修订

操作模型应知道“为后续自动化寻找可复现路径”这一质量目标；不需要知道框架 profile、IR、数据库或插件推送细节。先前“只说当前任务”的草案没有充分表达这项质量要求，当前以 exploration/prompts/operate_step.md 为实际规则正文。

本次从以下维度检查完整输入：语义要求可以多动作完成、命令成功与导航目标分开、规定方法与可选偏好分开、原值和批次参数保留、实际页面依据、Observe 与固定等待分开、恢复不擅自重置、完成边界只报告既有事实、对象选择语义、简短可追溯说明。输入与提交也分开：不偷偷追加回车，但允许完成搜索目标所必需的明确提交动作。

规定方法由 policy.py 同一份 MethodRequirement 生成给模型的说明并用于执行校验。返回应用首页不得用 Home、不得以 StopApp 自动恢复；第一阶段分类说明同步澄清应用首页与系统桌面。

上下文补充前台 package/activity、近期实际动作参数和完整的次数与时长账本。账本为派生视图，按参数和命令状态聚合整个块，保留 command_count、requested_total 与设备实际报告字段；不把请求量称为实测完成量，也不因缺少报告自动重复命令。

离线场景检查涵盖多次返回才能完成同一要求、规定方法的 schema/解码/策略一致性、近期历史裁剪后仍保留批次参数、部分失败与缺少设备计数不混同、固定等待与 Observe 分离。它们验证程序协议与模型可见信息，不等价于真实模型已经理解或稳定完成了这些任务；效果评估仍需固定真实用例与截图。
