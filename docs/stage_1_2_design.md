# 用例整理与手机探索设计（讨论稿）

历史设计稿。实际实现见 exploration_workflow_current.md 与 script_generation_current.md，下文提议和旧字段不代表当前代码。

日期：2026-11-11。基于当前工程实现设计；本文中的新增结构和机制尚未实现。

数据结构与文件归位的详细清单见 [前两阶段重构清单](stage_1_2_refactor_map.md)。取消循环探索策略后，本文的 ExplorationPlan 应理解为从 CaseSpec 派生的轻量执行视图；不必建立另一套独立持久化的步骤模型。目录和具体迁移方案以该清单为准。

## 1. 定位与设计结论

服务的产品目标是生成忠实于用户意图的自动化脚本。用户提供完整的操作流程、测试数据和验证预期；服务探索操作的实现方式，收集生成脚本所需的事实。业务预期是否正确，由生成后的脚本执行来检验。

建议保留当前“代码调度目标块、模型完成块内操作”的基础，迭代数据契约和探索闭环，不整体推翻现有工程。

三个阶段的交接如下：

```text
原始描述
  → 阶段一：整理、确认、结构化、校验
  → CaseSpec v2 + ExplorationPlan
  → 阶段二：按计划探索手机、记录动作和页面证据
  → ExplorationBundle
  → 阶段三：审查路径、组装 IR、编译验证、生成脚本
```

核心约束：

1. 用户的预期是脚本生成输入，不能被本次观察结果改写。
2. 探索不执行业务断言，不以业务断言成立作为继续或生成的条件。
3. 执行命令成功、操作目标完成、脚本可重复运行是三件不同的事。
4. 操作确实无法继续时，记录具体阻塞与已完成部分；不猜测、补造后续动作。
5. 第一阶段固定验证位置和循环作用域；第二阶段绑定页面证据；第三阶段不重新猜位置。
6. 原始轨迹记录事实，角色判断、路径筛选和定位质量结论放在独立的派生数据中。
7. 每个 step 只探索一遍；`repeat` 是代码生成元数据，不参与探索调度。不设置采样策略，也不由服务自动切换为执行 N 轮。

## 3. 阶段一：用户描述整理

### 3.1 一份语义模型，两种展示形态

当前“整理成文字 → 再用模型把文字解析一遍”的两次转换容易丢参数、循环范围和验证位置。

目标流程：

```text
原始描述 → 模型解析为 CaseSpec 草稿 → 程序校验
  → 从草稿渲染用户确认稿
  → 用户未修改：直接使用该草稿
  → 用户修改：基于修改稿重新解析、校验，形成新版本
  → 编译 ExplorationPlan
```

确认稿按原始顺序展示“操作 / 验证 / 重复区间”，验证紧随关联操作。不要再把所有验证集中移到末尾。界面可以另提供验证汇总，但不能让汇总替代顺序。

用户编辑后的确认稿是本次运行的语义来源；最初描述只留作审计。用户主动删除或修改的内容不能被覆盖率检查从旧描述中补回来。

保留原始描述、确认稿、版本和内容摘要；运行绑定已确认版本，不能在运行中静默重写。草稿和确认稿属于同一模型的不同表现，不各自维护另一套业务结构。

兼容现有插件时，可先继续接收 `editableText` 并在运行前解析；后续增加可选 `draftId/revision`，未编辑时避免第二次模型解析。草稿必须有明确的服务端存储和生命周期，不能仅新增一个无人保存的 ID。

### 3.2 操作块的粒度

操作块是一个可独立交接的目标，内部允许多个手机动作。以下位置用于划分块：

- 普通连续流程中，用户明确的中间验证位置可作为拆块边界。
- 循环开始、结束位置。
- 顺序或参数约束会因归并而模糊的位置。
- 一段流程过长，包含多个独立业务目标的位置。

不因“点击输入框、输入、点击提交”机械拆成三个目标块；但要在块内保留这些用户明确指令及顺序。自动补出的必要 UI 细节由第二阶段处理。

例如“搜索商品，验证结果包含 A，进入 A 的详情，验证价格”适合拆成搜索、进入详情两个块。若一轮重复流程整体是一个 step，则保留块内有序 instructions，在指令边界锚定中间验证，不为验证把一轮流程拆散后分别重复。

### 3.3 CaseSpec v2：一个权威结构

建议的最小骨架：

```text
CaseSpec
  schema_version
  case_name
  source_revision
  source_units[]       原始/确认文本的有序片段，供追溯
  steps[]             Step，按目标块顺序排列
  verifications[]     验证意图与明确锚点
  issues[]            解析歧义或信息缺失，不表示测试不通过

Step
  id, goal, repeat    repeat 默认 1，仅供第三阶段生成循环
  instructions[]      用户明确指令；语义粒度，不是插件动作清单
    id, text, parameters, source_refs[]
  source_refs[]

Verification
  id, goal
  anchor              {position: "before" | "after", step_id, instruction_id?}
  scope               "each_iteration" | "outside_repeat"
  source_refs[]
```

`goal` 是方便模型理解的摘要，`instructions` 和其中显式参数才是操作要求。校验和执行出现冲突时不能以摘要覆盖原始指令。不要让模型同时自由生成三份互相独立的同义要求。

`parameters` 只存用户明确给出的值，按指令类型支持有限字段，如 `text/app_name/target/direction/times/interval_seconds/duration_seconds`；没有写出的参数保持缺省。它是明确参数的抽取，不是预先生成底层 action。

程序为来源片段分配 ID，保存原文；模型返回引用，服务端检查引用有效性。涉及字面值时保留精确字符，不做双引号转中文引号、标点替换、大小写修改等语义性清洗。JSON 转义由序列化层处理。

### 3.4 示例：重复搜索并验证

输入：“启动商城；重复 3 轮：搜索‘手机’，验证结果包含‘手机壳’，返回首页；最后进入我的页面。”

以下示例省略 `source_units/source_refs/issues`：

```json
{
  "schema_version": "2.0",
  "case_name": "重复搜索后进入我的页面",
  "source_revision": "revision_001",
  "steps": [
    {
      "id": "step_001",
      "goal": "启动商城",
      "repeat": 1,
      "instructions": [
        {"id": "ins_001", "text": "启动商城", "parameters": {"app_name": "商城"}}
      ]
    },
    {
      "id": "step_002",
      "goal": "搜索手机后返回首页",
      "repeat": 3,
      "instructions": [
        {"id": "ins_002", "text": "搜索手机", "parameters": {"text": "手机"}},
        {"id": "ins_003", "text": "返回首页", "parameters": {}}
      ]
    },
    {
      "id": "step_003",
      "goal": "进入我的页面",
      "repeat": 1,
      "instructions": [
        {"id": "ins_004", "text": "进入我的页面", "parameters": {}}
      ]
    }
  ],
  "verifications": [
    {
      "id": "verify_001",
      "goal": "搜索结果包含手机壳",
      "anchor": {"position": "after", "step_id": "step_002", "instruction_id": "ins_002"},
      "scope": "each_iteration"
    }
  ]
}
```

锚点规则：

- 指向 `step_002/ins_002` 且 scope 为 `each_iteration`：脚本每轮搜索后验证，再执行返回首页。探索时只绑定这一遍的页面。
- 指向 `step_002` 的 after 且 scope 为 `outside_repeat`：脚本中整个循环结束后验证一次。
- 不填 instruction_id 时锚定整块边界；填入时必须引用该块内的指令。`outside_repeat` 只能锚定整块 before/after 边界。
- 指向第一块的 before 支持前置验证；指向最后块的 after 支持末尾验证。scope 不清楚时不能靠默认值猜测。
- 一个 repeat 表达整个块的一层重复；嵌套循环不能简单将次数相乘或拆成相邻块重复，无法无损表达时记录明确 issue，后续单独扩展。
- 第一版要求每条验证有明确锚点；原文确实无法确定位置时记录 issue，不能静默放到最后。

### 3.5 第一阶段应确定、应保留和不应推断的信息

| 情况 | 处理 |
| --- | --- |
| 文本、次数、方向、间隔、应用名称 | 保留原值，关联原始指令 |
| “连续上滑 5 次，每次间隔 3 秒” | 一个指令的手势参数，不建业务循环 |
| “A→B→返回 A，重复 5 轮” | 整轮作为一个 step，repeat=5；内部顺序保留为 instructions，探索只执行这一轮 |
| “确认订单” | 根据语义判断是点击确认还是业务检查，不能按关键词机械归类 |
| “进入订单列表检查订单” | 导航是操作，订单是否存在是验证，并保留二者顺序 |
| 自定义验证如“检查数据库订单状态” | 原样保留意图、已知调用名/参数；探索不执行它，不虚构实现 |
| 用户明确要求执行 SQL 作为流程准备 | 属于操作；手机插件无能力时报告能力缺口，不能偷偷当成验证跳过 |
| 验证不存在的提示/控件 | 不判用户预期错误；照常保留验证 |
| 验证为否定、数值比较、时间要求 | 完整保留表达式语义，不提前降级为“页面存在某文字” |
| 缺少输入数据、重复范围有歧义 | 记录具体 issue 与原文；不能猜值、猜循环范围 |
| 验证内含改变后续流程的数据提取或分支 | 拆出显式操作/数据依赖；当前不支持时指出边界，不能直接当普通静态断言 |

`issues` 区分阻塞编译的问题与不影响执行的说明。例如缺少登录账号会阻塞对应操作；没有数据库验证 API 只影响第三阶段该验证的实现，不阻止手机探索。默认不另加一轮确认，沿用已有确认界面展示问题。

### 3.6 程序校验与有界修复

模型负责语义整理，程序负责结构与可检查的忠实性：

1. ID 唯一；锚点和作用域合法；repeat 次数合法；操作顺序与来源引用有效。
2. 每个有执行/验证含义的原文片段均有去向；纯标题、说明允许标记为非执行内容。
3. 显式参数有来源，精确文本不得被规范化改写；同一来源被重复消费时需解释。
4. 不允许带验证的中间位置被吞进一个无法锚定内部位置的操作块。
5. 不允许模型偷偷补业务操作或将用户显式操作改成其他操作。
6. 格式、引用错误可把具体问题反馈模型修复，初始最多 2 次；语义歧义保留为 issue。

覆盖率校验能发现遗漏，不能证明自然语言完全等价。对参数、重复、验证范围复杂的用例增加一次针对性的忠实性复核；简单用例不默认增加独立模型调用。

### 3.7 ExplorationPlan：程序编译，不再交给模型改写

从 CaseSpec 确定性生成线性计划，包含：step 索引、前后顺序、块内指令和验证检查点。每个 step 只进入一次，不展开 repeat，也不生成采样策略。模型只执行当前块的一轮内容，不把 repeat 次数放进探索任务文本；它无权移动验证或改写用户数据。

不要构建另一份可独立编辑的语义用例。计划中的步骤通过 ID 引用 CaseSpec；缓存的渲染文本不是第二事实来源。

## 4. 阶段二：为生成脚本而探索手机

### 4.1 第二阶段的交付目标

除真实 action 外，还要交付：

- action 属于哪个步骤、哪条用户指令，以及哪次探索尝试（如存在恢复重试）。
- 动作前后观察、执行结果、坐标与实际下发参数。
- 操作块的开始/结束边界及完成依据。
- 每个验证锚点对应的实际 observation，而不是验证结果。
- 定位候选、匹配依据和使用限制。
- 试错/恢复/环境辅助的线索，以及未完成、结果未知的部分。

手机探索结束不等于已经证明脚本稳定。第二阶段提供带依据的素材；第三阶段负责路径审查、最终 IR 和编码。重复回放属于可选质量增强，不是前两阶段的默认业务测试。

### 4.2 外层由代码调度，内层由模型决策

```text
绑定用例版本、插件会话与设备
  → 初始观察
  → 外层遍历计划节点
      → 采集 before 检查点
      → 进入操作块，执行一轮内容，不读取 repeat 控制轮数
          → 构造上下文
          → 模型选择一个动作或声明完成/阻塞
          → 校验动作、关联指令
          → 先记录即将执行的 operation
          → 下发命令
          → 有界等待、观察结果
          → 补齐 operation 与进度账本
          → 无进展/错误处理，或继续
      → 完成块，采集 after 检查点
      → 保存块结果和快照
  → 输出 ExplorationBundle（包括部分完成结果）
```

完成判断针对“用户操作做到了什么”，不针对“用户业务预期是否成立”。例如输入错误密码并点击登录后，看到实际错误提示，就可以完成“提交登录”这个操作块；不需要匹配预期的“密码错误”。若下一块要求进入登录后的个人中心但实际无法进入，则在下一块报告操作阻塞，不能伪装页面已经到达。

### 4.3 用指令账本约束长块，避免模型遗忘和重复

保留当前块内的有序 `instructions`。运行时为每条指令记录：`pending/in_progress/done/blocked`，关联产生的 operation 与观察证据。

动作工具新增可选 `instruction_id`（无关业务指令的环境恢复可以为空）；服务端校验引用合法。`step_id/step_instance_id` 由调度器注入，不要求模型反复填写。一个指令允许多个动作，不把 instruction 强制等同于 action。

完成工具建议改为 `CompleteStep`，返回：`summary`、完成指令及证据引用。外部阻塞用 `ReportBlocker`；模型异常和执行故障由代码记录。避免把探索状态命名为 `passed`。

块内存在验证锚点时，在对应指令完成后使用 `CompleteInstruction` 这类非手机控制工具通知调度器，调度器绑定当前 observation 后才允许继续后面的指令。它只报告操作进度，不执行验证，也不新建 StepAgent。普通无锚点指令可继续采用动作关联与块结束对账，避免每条指令都增加一次模型往返。

代码检查是否还有显式指令未覆盖、固定次数是否对账、参数是否一致。不能只因模型调用完成工具就跳过未执行要求；对疑点进行一次针对性复核，不每轮额外调用评审模型。允许指令在初始页面已经满足，例如“进入首页”时已在首页，此时记录 observation 证据，不强制制造动作。

多次手势需由插件返回已执行数量或子动作结果。若只能确认总命令成功，标记证据粒度；若部分执行后失败，不假定执行次数为零并整组重试。

### 4.4 上下文设计

建议每轮包含：

```text
system：固定规则、工具约束、操作与验证边界
user：当前块 goal + 有序指令 + 原值参数 + 指令进度
      + 上一块简短实际结果 + 当前步骤在局部流程中的位置
assistant/tool：最近 N 个完整动作回合
user：最新 observation ID + 截图 + 必要页面元数据/局部控件
```

任务每次请求保留一份；历史按完整 assistant/tool 对裁剪，默认沿用 8 对。完整指令账本独立保存，不能随着最近 6 个动作摘要被裁掉。

常规决策只放最新截图。恢复或判断卡住时允许定向补充一张带明确时间标识的历史参考图，不把所有历史图片灌入上下文。默认不发送全量 UI 树；控件定位有歧义时提供局部候选。

模型不需要看到验证的预期值，以免为了匹配预期改变操作。调度器知道哪里需要采集检查点，模型只负责在那里完成操作。页面目标和明确指令已足够定义本块工作。

工具结果保留简洁，但允许必要的操作信息：`execution_status/message/observation_id`，批量动作增加实际计数。不能把结果未知包装成普通失败，也不能用“点击成功”暗示目标已经到达。

### 4.5 原值参数与动作校验

- 应用名、输入文本优先让工具引用当前指令参数，由程序解析成真实值；自由文字参数只用于用户未固定、且确实需要探索决定的内容。
- 每轮模型仍只选一个工具；参数范围、坐标、工具能力和指令引用由 Pydantic/代码校验。
- 工具限制不能改变用户要求。例如用户要求 20 次滑动而工具单次上限 10，计划执行两批并累计计数，不能截为 10。
- 用户明确等待 30 秒，按完整时长执行；页面稳定等待不抵扣这 30 秒。短工具可以分批，不能修改语义。
- 输入已有文本时，区分用户要求追加还是替换；清空/聚焦/提交行为需要记录并匹配插件实际能力。
- 保留当前 0–1000 决策坐标；记录它相对于哪张截图、屏幕旋转和尺寸，并保存实际下发像素坐标。坐标转换由程序完成。

### 4.6 观察与等待：获取可解释事实

Observation 在现有基础上增加：

```text
id, capture_started_at, capture_finished_at
device_ref, package, activity, screen_size, rotation
screenshot_ref（含实际图片尺寸）, elements_ref
capture_quality：完整/缺图/缺树/可能不一致，以及具体原因
```

优先演进插件为一次组合采集，返回截图与 UI 树的采集时间/版本；服务端用能力协商启用。组合接口也不宣称绝对原子，仍保留时间信息。兼容旧插件时继续串行采集，但检测采集前后页面是否明显变化，必要时有界重采。

允许截图可用但 UI 树不可用的页面继续视觉探索，并标记定位证据不足；截图本身不可用则不能继续盲点。

模型推理耗时也可能让截图过期。下发前检查 observation 年龄与已知页面变化；明显过期或页面已变时，先更新观察并重新决策，不拿旧 bounds 直接点击。过期阈值按页面动态程度配置，不能每轮无条件重拍后仍使用旧决策。

固定睡眠逐步替换为有界等待：短暂去抖 + 观察；若仍在明确加载/动画中，再有限观察。视频页、轮播页不要求像素完全静止。等待的目标是得到可操作页面，不是等待用户预期出现。

明确等待与系统稳定等待分开记录。瞬时提示场景在动作后尽早捕获初始帧，再等待稳定，保留两个观察的时间顺序；不因等待一秒后看不到提示而删除验证。

允许额外观察而不产生手机操作，因此不再使用 `len(observations) == len(operations) + 1` 作为全局约束。始终校验每个引用存在、时间顺序合法；`after_observation_id` 在观测失败时可以为空，但必须有原因。

### 4.7 执行记录与结果未知

一个 operation 建议具有：

```text
id, sequence
semantic_ref：step_id, instruction_id, step_instance_id
observation_transition：before_observation_id, after_observation_id
intent：tool_name, reason, raw_tool_args
requested_action：type, args, coordinate_space
dispatched_action：插件实际收到的参数、command_id
execution：pending/succeeded/failed/unknown，时间、错误类型、实际计数
```

先记录 pending 再发送命令。命令完成后补结果；截图采集失败不能让已下发动作从轨迹中消失。原始记录只追加或补齐执行状态，后续路径判断不覆盖事实。

RPC 超时表示“结果未知”，不一定表示“手机未执行”。提交、发消息、购买等动作不能直接重复。先重新观察并尝试核对原 command_id；仍不能确定则停止当前块并说明，不以再次点击赌结果。插件若尚不支持命令结果查询，保留该能力缺口。

### 4.8 试错、环境干扰与恢复

把推断放在独立的 `action_assessments` 中：`main/support/recovery/uncertain`、依据引用、后续是否存在偏离线索。执行模型的 reason 是线索，不是结果事实。

恢复原则：

- 关闭偶发提示、聚焦输入框、必要导航可以推进当前指令。
- 业务确认框、支付确认等可能是正常流程，不能统一当干扰删除。
- 不补登录账号，不替换业务对象，不改用户输入，不凭空重置应用数据。
- 不为获取验证材料而额外进入会改变状态的页面；所需导航应在第一阶段成为操作。
- 不因当前页面没有预期文本而恢复或重做操作。

沿用当前错误次数上限，并补两类检测：相近状态下重复相同动作、若干轮无指令进展。页面签名结合 activity、结构与截图特征；不能只靠 activity 判断页面是否变化。

触发后先刷新观察，再要求换策略；达到恢复预算即报告阻塞。模型格式错误、RPC/设备失败、页面无进展分开计数，不能所有问题共用一个“连续动作失败”。

预算分别约束每块动作轮次、恢复次数、模型修复次数、单命令超时与整段运行时长。按指令数量和明确等待时长估算初始预算，用户要求的等待不得被误算为卡住。预算耗尽只表示探索未完成，不表示业务用例失败。

前两阶段不把恢复动作直接删除；第三阶段按完整片段判断去掉绕路后，前后状态能否衔接。失败/未知动作虽通常不写入脚本，仍需保留给路径审查理解状态变化。

### 4.9 验证检查点：绑定证据，不执行断言

调度器在每个块边界或块内指令的 before/after 锚点保存：

```text
verification_id, anchor（step_id, instruction_id?, position）, step_instance_id
observation_ids[], primary_observation_id
capture_status：captured/unavailable
limitations[]
```

预期仍只存在 CaseSpec。检查点不返回 `passed/failed`，不拿实际文本替换预期。对于否定验证、预期控件不存在、自定义后台验证，都允许“证据有限但意图完整”。

UI 树可以供第三阶段确定定位；观察中没出现目标，不等于该验证应被删除。无法实现自定义验证时，第三阶段明确报告缺少适配规则。

before 检查点可复用最新但仍有效的 observation；after 检查点使用对应指令或整块实际结束的 observation。开始下一个动作前完成采集，避免页面已经离开。瞬态验证允许关联动作后多个帧，但不增加验证专用点击。

### 4.10 每块探索一次，repeat 仅用于生成代码

执行器按 steps 顺序，每块只执行一遍。不存在 `exact/sample_once` 策略选择、循环轮次调度或自动补跑。`repeat=N` 只由第三阶段读取，将该块整理后的有效动作与循环内验证整体包进 N 次循环。

例如 `goal=搜索手机后返回首页, repeat=3`：探索只执行搜索、返回首页这一轮；生成脚本是 `for ... in range(3): 搜索 → 循环内验证 → 返回首页`。不能分别生成“搜索三次，再返回三次”。

必须区分两种次数：

- 业务块 repeat：不进入探索次数控制，也不出现在模型的一轮任务文本里。
- 块内显式动作次数，如“连续上滑 5 次”：属于这一轮必须执行的指令参数，探索时完成全部 5 次。

`completed` 表示该块的一轮操作已探索完成，不表示原用例已经执行 N 轮，更不表示循环已经经过回放验证。检查点只绑定这一遍的事实；循环外验证可以复用单轮出口页作为有限上下文，但不得宣称它是 N 轮后的实际页面。

单次探索用于寻找操作模板，不保证证明模板在每轮都成立。生成时仍需保留相对目标、变量和动态定位意图，不能固化首次观察到的对象值。

若后续操作确实依赖累计 N 次才会出现的状态，则一次探索可能无法继续。服务记录具体依赖和缺失上下文，保留生成语义；不能擅自把执行模式改回 N 轮。是否支持这类数据依赖，是后续单独扩展的能力边界。

### 4.11 定位证据尽早采集，最终定位由生成阶段决定

保留现有 bounds 几何召回，前移或复用到每次动作的 before observation 上，输出带 ID 的候选。让模型选择候选 ID，服务端核对；匹配失败时保持 unresolved，不自动取第一个。

候选可包括 text、desc、resource-id、父子关系、同页匹配数、bounds；只使用插件实际返回并且目标框架可表达的能力。现有 light 树缺少信息时按需补采，不宣称已支持完整树定位。

区分“按指定商品名称进入”与“点击第一条结果”：后者是相对/序号意图，不能固定成本次第一条商品的名称。类似数字计数、价格、随机推荐内容的 text 也不能仅因同页唯一就认定稳定。

输出候选、匹配数和风险原因，如 `duplicate_label/dynamic_label/coordinate_only/tree_unavailable`。不输出未经验证的“稳定性分数”。最终 selector、回退策略和框架 API 映射留给第三阶段。

### 4.12 状态与交付物

步骤结果建议用 `completed/blocked/error`；完成结果允许有警告。整段探索用 `completed/partial/blocked/error/stopped`。外层 Run 的既有生命周期可以先保留，由 service 显式映射，避免一次修改整个插件协议。

交付物 `ExplorationBundle`：

```text
schema_version
case_spec                  已确认版本
exploration_plan           每块一次的顺序、块内指令、检查点和能力约束
trajectory                 原始 observations / operations
step_results               指令覆盖、开始/结束观测、实际完成摘要
verification_checkpoints   验证锚点 → 运行实例 → observation
target_evidence            定位候选和来源
action_assessments         可修订的角色/偏离判断
coverage                   未完成的单轮指令、未采集检查点
limitations                能力缺口与未知结果
status
```

没有手机操作的纯验证用例不假装完成了探索：可获取一次初始观察作为上下文，或交付无设备证据的用例给第三阶段。完全空用例不能静默生成空脚本并宣称完成。

正常生成默认需要每块所需的单轮操作已探索；不因 repeat>1 要求额外轮次。探索阻塞时仍保存 bundle；不把缺失动作伪装为完整脚本。第三阶段是否提供带缺口的草稿是单独的产品选择。

## 5. 模块落点和迁移顺序

### 5.1 建议模块

```text
case_preparation/
  schemas.py             CaseSpec/Step/Verification 的唯一公共定义
  prepare_cases.py        草稿编排与确认稿渲染
  structure_cases.py      模型解析适配
  validate_cases.py       引用/参数/覆盖/歧义检查
  execution_plan.py       CaseSpec → ExplorationPlan，复用并重写现有模块
  migrations.py          旧结构只在入口升级一次

mobile_execution/
  case_step_runner.py     目标块逐块一次、检查点调度
  loop_node.py            单操作块闭环
  progress.py             指令账本与次数对账
  checkpoints.py         验证观测绑定
  recovery.py             无进展与恢复预算
  tools/                  继续保留工具 schema / executor
  trace/                  继续保留事实记录，增加执行前登记

observations/
  store.py                采集、质量与时间一致性
  observation.py          观测协议

artifacts/
  exploration_bundle.py   导出、读取、版本校验；复用 snapshot_io 的拆图思路
```

文件数量可随实际实现合并；职责边界和一个权威 schema 比文件拆分数量重要。

### 5.2 推荐实施批次

1. **统一契约与顺序**：引入 v2 schema、验证锚点、step.repeat、块内 instructions、原值参数和单入口迁移。让现有生成侧在消费前显式识别版本；禁止新数据静默进入旧 IR。旧版本已丢失的位置不能靠机械迁移补造，标记 unresolved 或从原始描述重新解析。
2. **跑通最小探索交付**：计划编译、块内指令账本、步骤实例、检查点、partial bundle。先兼容现有插件命令，不依赖插件新增能力。
3. **提升执行可靠性**：执行前记录、unknown 结果、有界等待、观测质量、恢复预算、批量次数对账。
4. **提升生成证据质量**：候选 ID、动态与序号意图、按需 UI 信息、定位限制；同步改造第三阶段消费 bundle。
5. **增加可选优化**：疑难用例定向复核、插件组合观察与命令结果查询。不引入循环探索策略。

每批交付一条端到端可检查路径，不同时维持多套内部字段。迁移期间禁止猜测降级为旧协议；无法无损转换的 v2 用例应明确拒绝旧生成器消费。

## 6. 验收场景与效果指标

验收应使用固定输入和假插件/假模型验证契约，再用少量真实快照和手机流程评估效果；不要靠每次完整跑手机才能定位数据问题。

| 场景 | 必须表现 |
| --- | --- |
| 操作中间有验证 | 定位到块或块内指令边界；离开页面前采集；代码位置由锚点确定 |
| 用户预期与实际不同 | 验证保留原预期；不因此重试操作或中断探索 |
| 操作中包含“确认”按钮 | 正确保留点击，不按关键词误提取为断言 |
| 文本包含引号、空格、特殊符号 | 从输入到工具参数逐字符一致 |
| 滑动 20 次、等待 30 秒 | 支持分批且准确对账，不被工具上限截断 |
| repeat=5 的目标块 | 探索只执行该块一遍，生成完整块循环 5 次；无额外策略选择 |
| 循环内验证、循环后验证 | 指令锚点与生成 scope 明确区分，无错误重复或遗漏 |
| 累积循环与第 N 轮依赖 | 明确指出单轮探索的上下文缺口，不自动补跑 N 轮，不虚构结果 |
| 手机操作成功但截图失败 | 操作仍在轨迹，后观测标记缺失，可有界补采 |
| 提交命令超时 | 结果 unknown，先核对，不直接重复提交 |
| 页面有视频或动画 | 不以完全静止作为完成条件 |
| 无 UI 树的页面 | 可视觉探索，定位限制明确 |
| 偶发弹窗和走错后返回 | 全量事实保留，派生角色可供后续路径审查 |
| “点击第一条结果” | 保留序号意图，不固化本次结果文字 |
| 自定义验证无适配规则 | 手机操作照常探索；明确生成能力缺口 |
| 同设备并发两个任务 | 按设备串行；任务中固定设备，避免轨迹互相污染 |

同设备串行优先由插件按实际设备实施；服务端可先以 session 粗粒度排队。多会话可能连到同一设备，仅 session 锁不能解决，需要设备标识和插件侧约束；这属于保证证据可信所需的执行约束。

建议分开观察这些指标：输入指令/参数/验证锚点保留率、所需操作探索完成率、每块动作数与恢复动作比例、检查点采集完整率、定位证据覆盖率、模型调用/时间成本、最终脚本人工修改量。它们衡量生成质量，不统计业务断言通过率。

所有 bundle 都应能离线读取并重跑第三阶段。沿用现有 `snapshot_io` 的图片与 JSON 分离方式；保存 `step_results/checkpoints/coverage/schema_version`，成功、失败、停止都能交付已有材料。逐块保存并在关键动作前后补齐记录，避免仅结束时落盘导致异常后失去事实。
